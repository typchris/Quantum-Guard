# Quantum Guard Windows 1.12.3 Binary Audit

## Scope

This audit was performed against the supplied Windows 1.12.3 package and specifically `QuantumGuard.Engine.exe`.

The package does not contain the matching Go source tree, so this document records only findings directly supported by the compiled binary, Go function metadata, embedded source paths, strings, and call relationships.

## Confirmed local web proxy

The engine contains the endpoint:

`127.0.0.1:53679`

and the following functions:

- `main.applyLocalWebFilter`
- `main.stopLocalWebFilter`
- `main.writeWindowsUserProxy`
- `main.writeWebProxyPolicy`
- `main.closeWebConnections`
- `main.serveWebProxy`
- `main.flushWindowsDNS`

The engine also contains:

- `ProxyMode`
- `ProxyServer`
- `fixed_servers`
- `Software\Policies\Google\Chrome`
- `Software\Policies\Microsoft\Edge`
- `InternetSetOptionW`
- `browser-web-proxy.json`

The exact response strings `Destination unavailable`, `Unsupported destination`, and `Tunnel unavailable` are present in the engine.

Therefore a browser page displaying `Destination unavailable` while traffic is routed through Quantum Guard is generated by the Quantum Guard proxy path.

## Confirmed cleanup call path

Go function metadata identifies:

- `main.applyLocalWebFilter`
- `main.stopLocalWebFilter`
- `main.exitApplication`
- `main.watchdogMode`
- `main.mainWndProc`
- `main.main`

Disassembly confirms `stopLocalWebFilter` performs the local proxy teardown sequence, including calls to:

1. `writeWindowsUserProxy`
2. `writeWebProxyPolicy`
3. `closeWebConnections`
4. listener/state cleanup

The only confirmed direct call to `stopLocalWebFilter` from the application lifecycle is at the tail of `main.main`, after the Win32 message loop ends. Embedded source mapping identifies this as `main.go:4637`.

No direct call from `exitApplication` or `watchdogMode` to `stopLocalWebFilter` was found.

This is a reliability gap. Graceful message-loop termination reaches cleanup, but forced process termination cannot execute cleanup, and the watchdog restart path does not first guarantee that stale QGuard proxy configuration has been restored.

## Windows shutdown risk

No explicit `WM_QUERYENDSESSION` or `WM_ENDSESSION` handling was confirmed in the current engine audit.

The permanent 1.12.4 implementation must perform bounded proxy cleanup on Windows session shutdown instead of depending only on the normal message-loop tail.

## Web Protection OFF

The engine contains the status text:

`Web Protection is off. Browser traffic passes through without category or ad filtering.`

This shows that 1.12.3 may intentionally keep browser traffic going through the local proxy even when Web Protection is OFF.

That design increases the blast radius of any proxy transport bug. If no other active Quantum Guard feature requires browser interception, 1.12.4 should prefer restoring direct browsing. If the proxy must remain active, pass-through mode must be health checked and must have bounded connection timeouts.

## Cloud authentication findings

The engine contains:

- `main.startGoogleSignIn`
- `main.startExistingDeviceReconnect`
- `main.validateCloudSignInIdentity`
- `main.refreshCloudTokenIfNeeded`
- `main.loadCloudState`
- `main.persistCloudSessionLocked`

It also contains the user-facing message:

`Use the existing Google account for this managed device. Its pairing has been preserved`

The binary does not contain references to the newer RPC names:

- `recover_my_device_v2`
- `enroll_device_v2`
- `claim_device_installation`

Therefore 1.12.3 cannot be relying on the new server-authorized recovery/enrollment flow now available in Supabase.

The permanent fix is to make authenticated Supabase device context authoritative after PKCE succeeds rather than treating a stale cached local user ID as final authority.

## Temporary mitigation

The hotfix branch contains:

- `QGuard-Network-Recovery.ps1`
- `QGuard-Network-Guardian.ps1`
- `Start-QGuard-NetworkSafe.ps1`
- `Start Quantum Guard - Network Safe.cmd`

These are QA mitigations only. They do not replace the required in-engine 1.12.4 lifecycle changes.

## Release decision

Windows 1.12.4 should remain blocked until:

- proxy cleanup is explicit on normal exit
- Windows session shutdown is handled
- watchdog recovery repairs stale proxy state before restart
- startup repairs orphaned QGuard proxy state
- Web Protection OFF cannot leave browsing dependent on a failed proxy
- cloud identity recovery uses the authenticated Supabase device context
- a stable Windows installation ID is persisted and reused
- repeated upgrades do not create duplicate Windows device rows
